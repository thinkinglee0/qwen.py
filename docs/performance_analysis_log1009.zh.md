# 性能分析 —— 一个引擎、两台宿主、同一块 GPU（log1009）

> 英文原版：[`performance_analysis_log1009.md`](./performance_analysis_log1009.md)

**这一轮测的是"测量"本身。** [log1003 §2.4](./performance_analysis_log1003.zh.md) 断言 qwen.py 的设备
工作是可迁移的、而吞吐由宿主 CPU 决定，但那是从相隔一天租到的两台机器上**推断**出来的。log1009 直接
验证它：同一个提交、同一个负载、两台 vast 实例，**同一块型号的 GPU**、截然不同的宿主，背靠背跑完。

一句话版本：**两块 GPU 没有差别，只是其中一块接在一颗 2016 年的 Xeon 上。**

**数据来源**

`smp_prep`/`smp_pen`/`smp_pick`/`smp_post` 拆分和 `upd_proj`。

## 摘要

1. **设备工作完全相同。** batch 512、纯 decode：`gpu_busy_from_trace` **27 053 对 27 032 µs/步
   （−0.1 %）**，采样器的 event 区间一致到小数点后三位 —— `smp_gpu` 16.348 对 16.349、
   `smp_pen_gpu` 6.848 对 6.846、`smp_pick_gpu` 8.858 对 8.864。七个 batch 全部在 **±3 %** 内。
2. **吞吐却差到 2.3 倍。** batch 1 **66.2 对 29.6 tok/s**、batch 64 **3 645 对 1 647**，到 batch 1024
   收敛成 **1.01×**。峰值 **11 117 @ batch 512** 对 **9 580 @ batch 1024** —— 宿主 2 要两倍并发，
   而且始终没追上。
3. **原因是宿主的单线程速度。** Ryzen 9 5900X（Zen 3，2020）对 Xeon E5-2680 v4（Broadwell-EP，2016）。
   batch 512 上**十三个互不相关的主机侧字段全部落在 2.03×–2.35×** —— 一个均匀的惩罚，这是解释器整体
   变慢而不是某处有瓶颈。但要注意**没有**被确立的部分：[runbook §1b](../env/vastai/vast-evn-build.md)
   的解释器基准在两台宿主上都**没跑**，所以本报告能把差距归因到 CPU，却无法把它分解成频率与 IPC
   （§4.1）。
4. **不是 PCIe，尽管看起来很像。** 宿主 2 的链路协商成了 **gen 1**（`pcie.link.gen.current = 1`，
   max 3），对宿主 1 的 gen 4 × 16。但 decode 步不在乎：每步 `Memcpy HtoD` **4.6 对 4.7 µs**、
   DtoH 1.2 对 0.9 µs、DtoD 0.621 对 0.621 ms。链路只在启动时那一次 0.99 GB 权重加载上起作用。
5. **也不是功耗或温度。** 宿主 2 的 enforced 上限是 **500 W**，比宿主 1 的 450 W **更宽**。宿主 1 有
   5.3 % 的 busy 样本触发 `sw_power_cap`，中位 389 W / 2 715 MHz，最高 73 °C。
6. **只有一个字段被打得比那个均匀的 2.1× 更狠：`bld_meta`，3.0–3.5×。** 它是整步里最纯 Python 的阶段
   —— 五个对 batch 的列表推导加一次 `chain.from_iterable` 展平 —— 所以几乎没有 C++ 张量工作来稀释
   解释器惩罚。它因此成为下一个 `.item()` 型目标（§5）。
7. **新的计量立刻见效：batch 512 上采样器那 16.35 ms/步拆成 `smp_pen` 6.85（42 %）和
   `smp_pick` 8.86（54 %）**，`smp_prep` 0.59、`smp_post` 0.04。这是
   [log1001 §7.1–7.2](./performance_analysis_log1001.zh.md) 要修的东西**第一次被分别定价**（§6）。
8. **log1003 那条"比值可迁移、绝对值不可"在第三台宿主上成立。** batch 1 上 qwen.py 对 vLLM 臂 A：
   log1003 的 EPYC 上 **1.64×**，这里的 Xeon 上 **1.53×**，而绝对吞吐从 43 掉到 29.6 tok/s。
9. **`.tolist()` 修复完全按预测落地。** batch 512 上 `aten::item` **515 → 3**、
   `_local_scalar_dense` 515 → 3、`select` 517 → 5、`as_strided` 1 041 → 529；每步 aten 调用总数
   **6 158 → 4 112（−33 %）**，而且现在与 batch 无关。

## 2. 方法

### 2.1 固定了什么

两台宿主同一个提交，并且是从 dump 核实的而不是假定的：`top_k=20, top_p=0.8`、`compile_rope=false`、
`pre_gather_cos_sin=true`、`max_model_len=1024`、`max_num_batched_tokens=8192`、
`num_blocks=4096 × block_size=256`。负载是 `test_benchmark_sweep_batch_size`：10 × batch 个请求
（最少 64）、固定 512 入 / 128 出、`ignore_eos`。**两台宿主全部 33 个 sweep 点上零抢占、零错误。**

### 2.2 怎么读 `*_gpu` 字段

如 [log1001 §2.2](./performance_analysis_log1001.zh.md) 所确立，`fwd_gpu` / `rope_gpu` / `smp_*_gpu`
是流上的 CUDA event 区间，不是 kernel 累加：主机成为瓶颈时它们里面含气泡。宿主 2 在 batch 512 上空闲
31 %、batch 64 以下空闲 86–91 %，**所以它被饿着的地方 event 区间都被虚高了** —— batch 512 上
`rope_gpu` 读出 4.18×、`fwd_gpu` 2.05× 正是这个原因，而权威的 `gpu_busy_from_trace` 只差 0.1 %。

贴着真 kernel 的那些区间说的是真话，那就是采样器的：batch 512 上宿主 1 只有 3.1 % 空闲、采样器占整步
60 %，所以 `smp_gpu` 及其子项在两边都没有气泡。§3.1 引用的就是这些。

### 2.3 噪声地板

| | 宿主 1 | 宿主 2 |
| --- | --- | --- |
| sweep 重复 | **1 次**（没有 `benchmark_baseline2`） | 2 次 |
| 吞吐 run 间 | — | 最差 **1.59 %**，中位 0.71 % |
| profile 重复 | 2 次 | 2 次 |
| batch 512 超 2σ 字段 | 9/31 | 8/27 |
| 抢占 / 错误 | 0 / 0 | 0 / 0 |

**宿主 1 的吞吐数字没有 run 间地板** —— 只跑了一次 sweep。考虑到同一份代码在宿主 2 上最差只有
1.59 %，§3.2 那些 2.0–2.3× 的比值是任何可能噪声的约 100 倍，所以结论是安全的；但按
[runbook §6e](../env/vastai/vast-evn-build.md) 这是个欠缺，最便宜的补法是下次多跑一轮。

## 4. 为什么 —— 以及不是什么

### 4.1 CPU 单线程 —— 归因是扎实的，分解没有被测量

**数据支持的部分。** 这个惩罚在**十三个互不相关的主机侧字段上是均匀的**（§3.3），而设备侧一致到
±0.1 %。这个组合排除了所有查过的替代解释 —— PCIe（§4.2）、功耗与温度（§4.3）、kernel 或配置差异
（§2.1）—— 剩下的就是宿主执行 Python decode 循环的能力。跑这个循环的 CPython 接近一个纯单线程
整数/指针追逐负载：[log1001 §7.3](./performance_analysis_log1001.zh.md) 量到每步约 4 400 次
`aten::` 调用，其中 71–80 % 根本不发 kernel。

**数据不支持、但本节早先的草稿照样声称了的部分。** 那份草稿把 2.1× 分解成"频率 1.45× × IPC 约
1.5×"。**那个 IPC 数字既没测也没有出处 —— 它是从答案倒推出来的（2.2 ÷ 1.45），然后被当成"乘积独立地
预测了实测值"来呈现。这是循环论证，已删除。** 关于这两颗 CPU，这里真正已知的是：

| | Ryzen 9 5900X | Xeon E5-2680 v4 | 状态 |
| --- | --- | --- | --- |
| 微架构 | Zen 3（2020） | Broadwell-EP（2016） | 厂商事实 |
| 标称 boost 频率 | 4.8 GHz | 3.3 GHz | 厂商事实 —— **1.45×** |
| **run 期间的实际运行频率** | — | — | **未记录** |
| **这个负载上的 IPC** | — | — | **未测量** |
| **解释器循环耗时** | — | — | **未测量 —— §1b 那项没跑** |
| 实测主机字段惩罚 | — | — | **2.03–2.35×** |

标称频率比不能独自承担这个论证，有两个原因：两台宿主的持续频率都没采样（宿主 2 的 Xeon 跑在共享服务器
28 核里分到的 14 核上，可能根本到不了 3.3 GHz），而一个跨四年、两代微架构的差距，贡献很可能比频率更大。
诚实的说法是：**这两颗 CPU 之间有约 2.1× 的单线程差距并不意外 —— 而不是"它被预测出来了"。**

**补救只需要一条命令，而且已经在 runbook 里了。** log1003 之后加进
[§1b](../env/vastai/vast-evn-build.md) 的那个 3 M 次纯 Python 循环，正是用一个数字量这件事的 ——
log1003 的参考值是 EPYC 7402 被压在约 2.24 GHz 时的 276 ms。**这次两台宿主都没跑**，`uptime` 和
`scaling MHz` 也没采（§8.6）。跑了的话，本节会有一个测量值，而不是一个合理性论证。**这正是那道闸门
存在的全部理由。**

内存延迟是另一个未经检验的贡献者：宿主 1 是桌面 B550 上的 DDR4-3200 双通道，宿主 2 是 X99 服务器平台，
它的四通道带宽对一个受延迟限制的解释器毫无帮助。同样未测量。

### 4.2 不是 PCIe —— 最明显的嫌疑，实测后排除

宿主 2 的链路跑在 **gen 1**，而主板支持 gen 3；对宿主 1 的 gen 4 来说是八倍的带宽差。而它对这个负载
**无关**：

| 每 decode 步，batch 512 | 宿主 1 | 宿主 2 |
| --- | --- | --- |
| `Memcpy HtoD` | 0.0046 ms | 0.0047 ms |
| `Memcpy DtoH` | 0.0012 ms | 0.0009 ms |
| `Memcpy DtoD` | 0.6210 ms | 0.6212 ms |

**每步只有 4.7 µs 的主机→设备流量。** 原因是 M8 的常驻 buffer 设计：staging 张量只有几 KB
（slot index、want、needs-sample、cache slots、block table），token 回读是 `B` 个 int32。链路只出现
一次 —— 启动时那 0.99 GB 权重加载，gen 1 下约 0.3 s 对 gen 4 的约 0.04 s，在稳态里看不见。

这值得记一笔，因为 log928 曾把 gen-1 链路列为**那一轮**数字的一条警告。在常驻 buffer 的 decode 负载
上，它不是。

### 4.3 也不是功耗、不是温度

宿主 2 的 enforced 上限是 **500 W，比宿主 1 的 450 W 更宽** —— 余量更多而不是更少。宿主 1 的轨迹显示
5.3 % 的 busy 样本处于 `sw_power_cap`，中位 389 W / 2 715 MHz，最高 73 °C，无热降频。宿主 2 在自己
sweep 期间没有 GPU 轨迹（§8），但 ±0.1 % 的设备时间一致是更强的论据：**降频程度不同的两块 GPU 不可能
给出相同的 kernel 时间。**

## 5. `bld_meta` —— 唯一比解释器惩罚更糟的字段

| | batch 1 | batch 64 | batch 512 |
| --- | --- | --- | --- |
| `bld_meta` h2/h1 | 3.00× | **3.52×** | 3.13× |
| 其他每一个主机字段 | 约 2.0× | 约 2.2× | 约 2.1× |

`build_attn_metadata` → `RequestBuffer.set()` 是整步里最纯 Python 的阶段：

```python
self.slot_idx_np[:bsz]     = [r.slot for r in reqs]
self.want_np[:bsz]         = [s.want for s in s_infos]
self.needs_sample_np[:bsz] = [r.projected_is_decoding or
                              (r.num_scheduled_tokens + s.want == r._num_projected_prefill_tokens)
                              for r, s in zip(reqs, s_infos)]
cache_slot_flat            = list(chain.from_iterable(s.cache_slots for s in s_infos))
```

五个对 batch 的列表推导 —— 其中一个每个元素还带一个复合判断 —— 加一次 O(总 token 数) 而非 O(batch)
的展平，然后从 Python list 写进 numpy。其他主机侧字段多少有 C++ 张量调用来稀释解释器惩罚，这一个几乎
没有，所以它承受那 2.1× 再乘上去。

**这和本报告 §7.2 确认已修的 `.item()` 循环是同一型的发现**，而且它现在是剩下最大的随 batch 增长的
主机成本。宿主 1 上 batch 512 它是 27.9 ms 步里的 0.615 ms，天花板不高 —— 但在宿主 2 那样的机器上，
或者在 batch 128–256（**两台机器都是主机瓶颈**的区间），它就是下一个值得批量化的东西。

## 6. 新的采样器拆分说了什么

log1003 之后新加的 `smp_prep` / `smp_pen` / `smp_pick` / `smp_post` 事件给出了采样器**第一次**被实测的
分解。宿主 1、batch 512、纯 decode，那里 GPU 只空闲 3.1 % 所以区间就是 kernel 时间：

| | ms/步 | 占采样器 | 占整步设备时间 |
| --- | --- | --- | --- |
| `smp_prep` —— `build_sampling_tensors` | 0.592 | 3.6 % | 2.2 % |
| **`smp_pen` —— `apply_penalties`** | **6.848** | **41.9 %** | **25.3 %** |
| **`smp_pick` —— `sample()`** | **8.858** | **54.2 %** | **32.7 %** |
| `smp_post` —— `add_sampled_tokens_on_device` | 0.041 | 0.3 % | 0.2 % |
| **`smp_gpu` 合计** | **16.348** | 100 % | **60.4 %** |
| `gpu_busy_from_trace` | 27.053 | | 100 % |

嵌套关系自洽：`prep + pen + pick + post` = 16.338 对 `smp_gpu` 16.348；`pen + pick` = 15.705 对
`smp_run_gpu` 15.710。

**这让 log1001 §7.1–7.2 的两半第一次被分别定价：**

* **§7.2 稀疏 penalties，现在有数字了：6.85 ms/步。** `apply_penalties` 必须跑在 `topk` 之前（它改变
  排序），所以搬不进候选窗口 —— 但它是一次**稀疏**更新，最多碰 151 936 列里的
  `prompt_len + output_len ≤ 1 024` 个，0.7 %。gather、apply、scatter 回去，替掉六遍全词表 pass。
* **§7.1 窗口内采样，瞄准 8.86 ms 的大部分。** 其中 `topk` 本身约 1.86 ms 且不可约；其余是全词表的
  尾巴 —— temperature、`-inf` 的 scatter 回写、fp32 softmax、死行保护、`multinomial`、`argmax`。

两者合计约 16.35 ms 里的 13 ms，即采样器降到约 3.5–4 ms、设备步从 27.05 降到约 14 ms。log1003 §6.4
提的"先做哪一半"现在仅凭体量就能回答：**两者相差不到 30 %，所以先做更容易保证正确的那个** —— 而
§7.1 的窗口改造已经做了一半。

小 batch 的警告：batch 128 以下宿主 1 空闲 50–80 %，那些 `smp_*_gpu` 区间含气泡，pen/pick 的占比在
8 % 到 53 % 之间乱跳，没有意义。这里只有 batch 256 和 512 可信。

## 7. 这一轮验证了两件事

### 7.1 比值可跨宿主迁移，绝对值不行

[log1003 §2.4](./performance_analysis_log1003.zh.md) 论证过：两个主机瓶颈循环之间的比值与解释器速度
无关，并用它救回了小 batch 的数据。宿主 2 在被停掉之前跑完了 vLLM 臂 A（无 compile、无 graph）的
batch 1–2 —— 那速度下每轮 3 分钟 —— 刚好够在第三颗 CPU 上检验这个论断：

| 宿主 | CPU | qwen.py | vLLM 臂 A | 比值 |
| --- | --- | --- | --- | --- |
| log1003 | EPYC 7402 @ 约 2.24 GHz | 43.0 | 70.8 | **1.64×** |
| log1009 宿主 2 | Xeon E5-2680 v4 | 29.6 | 45.1 | **1.53×** |

batch 2 上是 1.64× 对 1.54×。**绝对值变了 0.69 倍，比值保持在 7 % 以内。** 小 batch 上对 vLLM eager
路径的引擎设计差距，在任何宿主上都是约 1.5–1.6×。

### 7.2 `.tolist()` 修复做到了预测的事

上一轮预测把 `want_stage_snapshot[i].item()` 换成一次 `tolist()` 之后，batch 512 的调用数会从
515/517/515 降到"3/5/3"：

| aten 调用/步 @ batch 512 | log1003（修复前） | 宿主 1 | 宿主 2 |
| --- | --- | --- | --- |
| `aten::item` | 515 | **3** | **3** |
| `aten::_local_scalar_dense` | 515 | **3** | **3** |
| `aten::select` | 517 | **5** | **5** |
| `aten::as_strided` | 1 041 | 529 | 532 |
| **合计** | **6 158** | **4 112** | **4 118** |

每步 aten 调用少了 **33 %**，而且现在与 batch 无关，稳在约 4 100 —— 正是 log1003 §2.4 指出的那个固定
地板。为测量它而加的 `upd_proj` 在 batch 512 上读出 0.097 ms/步。也如预测：**batch 512 上没换来吞吐**
（那里是设备瓶颈）、**batch 1 上也没有**（只有 15 次调用）；它的价值在 batch 128–256。

## 8. 注意事项

1. **宿主 1 只有一次 sweep，不是两次。** 它的吞吐列没有 run 间地板。宿主 2 在同一份代码上 1.59 % 的
   最差值是现有的最佳替代。
2. **宿主 2 在自己 sweep 期间没有 GPU 频率/功耗轨迹** —— 只有 vLLM 那次，而那时 GPU 利用率从未超过
   50 %，所以轨迹里没有 busy 样本。降频是靠设备时间一致间接排除的，不是直接测的。
3. **宿主 2 的 vLLM 臂只覆盖 batch 1 和 2。** 够做 §7.1 的比值检验，不够做 sweep。
4. **`*_gpu` 是 event 区间而非 kernel 累加**（§2.2）。宿主 2 在 batch 512 上 `fwd_gpu` 的 2.05× 和
   `rope_gpu` 的 4.18× 是气泡，不是更慢的 kernel；要信的是 `gpu_busy_from_trace`。
5. **prefill 延迟在 batch ≥ 256 上反转** —— 宿主 2 报出的 prefill **低于**宿主 1（256 上 117.8 对
   125.6 ms，512 上 141.1 对 164.8）。可能是宿主 1 准入更快、因此每步攒了更多 prefill chunk 的二阶
   效应，但本报告没有数据来确立它。**记录，不解释。**
6. **完全没有采集主机侧的测量。** [§1b](../env/vastai/vast-evn-build.md) 和
   [§6e](../env/vastai/vast-evn-build.md) 要求的解释器循环、`uptime`、`scaling MHz` 在两台宿主上都
   不存在，所以 §4.1 的归因靠的是惩罚的**均匀性**而不是一个直接数字，而且两台宿主的实际运行频率和
   邻居负载都未知。下次每台一条命令。
7. **和 log1001/log1003 的跨 log 比较混杂了代码与宿主两个变量。** log1009 跑的是更新的提交（采样器
   拆分、`upd_proj`、`.tolist()` 修复）。设备侧没变 —— batch 512 的 `gpu_busy` 这里是 27 053 µs，
   log1001 是 27 305 —— 所以 §6 的采样器工作依然欠着，但跨这些 log 的 TPOT 比较并不干净。

## 9. 接下来

1. **把采样器做完，用 §6 的数字排序** —— penalties 6.85 ms、pick 8.86 ms，27 ms 的设备步里可回收约
   13 ms。这仍然**大于**对 vLLM 实测的整个差距（[log1003 §3.2](./performance_analysis_log1003.zh.md)）。
2. **把 `RequestBuffer.set()` 的列表推导批量化**（§5）。和 `.item()` 修复同一型，现在是最大的随
   batch 增长的主机成本，在 batch 128–256 上收益最大。
3. **做引擎对照要租宿主 1 那一类机器。** 一颗 Zen 3 桌面 CPU 把拐点放在 batch 256、batch 512 上只有
   3.1 % 空闲；一颗 Broadwell 服务器 CPU 把引擎整个 sweep 都按在主机瓶颈区，那里的测量说的是 CPU 而
   不是引擎。log1003 之后加进 [runbook §1b](../env/vastai/vast-evn-build.md) 的那道解释器闸门，就是
   用来在花钱之前把两者分开的。
4. **把 §1b 和 §6e 本来就要求的主机侧测量跑起来** —— 3 M 次解释器循环、跑完后的 `uptime`、
   `scaling MHz`、`os.sched_getaffinity`。四条命令、一分钟，而它们决定 §4.1 是一个**测量**还是一个
   **论证**。log1003 在 EPYC 7402 上的 276 ms 是项目目前唯一的参考点；再来两个就能形成标尺。
5. **每台宿主都补上第二轮 sweep**（§8.1），并且让 GPU 轨迹在 qwen.py 的 sweep 期间也跑着，而不是只在
   vLLM 臂上跑（§8.2）。
