## 摘要

1. **采样就是引擎本身。** batch 512 时它占**整轮墙上时间的 60.4 %**、每个 decode 步的 73 %；
   batch 1024 时占单步的 82 %。它**随 batch 线性增长** —— batch 1 时 1.1 ms，batch 1024 时
   139.8 ms，1024 倍的 batch 对应 **127 倍**的增长。
2. **模型前向无论喂多少 token 都是约 22 ms。** `fwd_gpu` 从 batch 1 的 20.50 ms 到 batch 1024 的
   23.47 ms：**1024 倍的 token 只涨 14 %**。其中的 `rope` 在整个 sweep 上的变化不超过 4 %。
3. **峰值吞吐 5095 tok/s**，而最后一次划算的翻倍停在 **batch 128** —— 到 256 时，每增加一单位延迟
   只换回 0.70 单位吞吐。
4. **复现性很好**：11 个点两次 run 全部在 **1.21 %** 以内，四个最大的 batch 在 0.5 % 以内。
   约 1.5 % 以下都算噪声；本文的每一项发现都在 5 倍到 127 倍之间。

## 1. 被测系统

### 1.1 硬件

NVIDIA RTX 4090（24 GB GDDR6X），vast.ai 实例 —— **与 log914 不是同一台**。
峰值 HBM 带宽 1008 GB/s；峰值 BF16 稠密算力（FP32 累加）165.2 TFLOP/s。

### 1.2 模型

Qwen2.5-0.5B-Instruct，`torch.bfloat16`。494.03 M 参数 = 357.9 M 主体 + 136.1 M embedding / LM
head；**0.988 GB** 的 BF16 权重；每 token 12 KiB 的 KV。

### 1.3 引擎配置

| 项 | 值 |
| --- | --- |
| `max_model_len` | 1024 |
| `max_num_batched_tokens` | 8192 |
| `long_prefill_token_threshold` | 8192 |
| `num_blocks` × `block_size` | 4096 × 256 → **12.0 GiB** KV |
| `max_num_seqs` | 扫 1 → 1024 |
| `use_d_first_schedule` | **false** |
| 采样 | `do_sample=true`、`do_penalities=true`、`temperature=0.7`、`top_k=20`、`top_p=0.8` |
| 注意力 | `flash_attn_varlen`（paged） |
| 优化开关 | 全关（见上面的提示框） |

## 2. 方法

合成的固定形状负载：每个请求都是 **512 个随机 token id 进、128 个 token 出**，忽略 EOS，
`req_num = max(64, 10 × batch)` 全部预先入队，由 `run_to_completion()` 排空。闭环饱和，所以报出的
`queueing` 和 `ttft` 是入队排队的产物，不是延迟指标。

**噪声地板是测出来的，不是假设的。** 吞吐，第 2 轮相对第 1 轮：

| batch | 1 | 2 | 4 | 8 | 16 | 32 | 64 | 128 | 256 | 512 | 1024 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Δ | +0.30 % | −0.58 % | −0.78 % | +0.26 % | +1.21 % | −0.40 % | +0.26 % | +0.96 % | +0.36 % | +0.50 % | +0.47 % |

最差 **1.21 %**，而 log914 是 5.5 % —— 当时噪声最大的小 batch 点，现在和大 batch 一样紧。

本 harness **不受**开关报告 §1.2 描述的 profiler 污染影响
（见 [`performance_switches_log915.zh.md`](./performance_switches_log915.zh.md)）：它从不进入
`torch.profiler`，一次 session 里 11 次建 engine，host 侧字段是平的。**两个 harness 的数字打架时，
以这一份为准。**

## 4. 瓶颈，按代价排序

### 4.1 采样 —— batch 512 时占整轮的 60.4 %

**证据。** `sample_gpu` 在 batch 512 是 100.2 ms 步里的 73.2 ms，batch 1024 是 171.3 ms 里的
139.8 ms —— 设备侧数据，所以是真实的 kernel 工作。算上混合步，batch 512 整轮 139.3 s 里采样占
84.2 s。它随 1024 倍 batch 增长 **100 倍**，而其他每步成本要么持平、要么次线性。

**根因 —— 每步两趟全词表遍历。**

* [`apply_top_p`](../src/qwen/sampling.py#L200) 对每个序列的完整 151936 宽的行做排序 —— batch 512
  时是**每步 7800 万个元素的排序**，batch 1024 时 1.56 亿。
* [`apply_penalties`](../src/qwen/sampling.py#L157) 物化 `[batch, vocab]` 的 fp32 张量；仅
  `rep_pen[:, None].repeat(1, vocab_size)` 一项在 batch 512 时就是 311 MB、**batch 1024 时 622 MB**，
  每步写一遍再读回来，之后还有约 7 趟全量遍历。

**修法。** 先砍到候选集：`top_k = 20` 时，top-p 只需要给 20 个幸存者排序，而不是 151936 个。
`torch.topk(logits, k)` → 在 *k* 个候选上 sort / softmax / `multinomial` → 把选中的 id 散射回去。
penalty 改在 gather 出来的候选集上做，或者融进 logits 那一趟。

**收益。** 采样快 5 倍，batch 512 端到端吞吐约 **2 倍**；而且通过 §3.4 的 prefill 步再赚一次。

### 4.2 模型前向无论喂多少 token 都是约 22 ms

**证据。** `fwd_gpu` 在 batch 1 是 20.50 ms，batch 1024 是 23.47 ms —— **1024 倍 token 只涨 14 %**。
一个携带 7511 个 token 的 prefill 步花 77.3 ms，即 7 倍的 token 换来 3.4 倍的时间，这是整个 sweep
里前向唯一表现得像"计算"的地方。

batch 1 时这个固定成本占**整步的 90 %**，把单流吞吐钉死在 43.6 tok/s。其中 `rope` 一项就是 6.2 ms
—— 占 28 %，且横跨整个 sweep 不变。

**根因。** 逐层的 eager 派发：24 层 × 约 12 个 kernel，每个都要付 Python、dispatch 和 launch 的成本。
[profile harness](./performance_switches_log915.zh.md) 测得 decode 步里 GPU 有 50~85 % 时间空闲 ——
那是同一件事的设备侧说法。

**修法。** 把 decode 路径做成 **CUDA graph**（batch 固定后形状就是静态的），或
`torch.compile(mode="reduce-overhead")`。这是唯一能改善单流延迟的改动。注意 kernel 级别的调优在这里
**帮不上忙，而且实测有害**：`compile_rope` 拿掉 0.4 ms 的 GPU 工作，却加上 1~4 ms 的墙上时间。

### 4.3 token 回读会阻塞，而且比 batch 涨得更快

`dth` —— [`engine.forward`](../src/qwen/engine.py#L71) 里的 `next_tokens.tolist()` —— 从 batch 1 的
0.03 ms 涨到 batch 1024 的 **5.24 ms**，**182 倍**，而且它是一个硬同步点。采样内部还有两个阻塞同步
（`apply_top_k` 里的 `.item()`、`sample` 里的 `dead.any()`）。

排在 §4.1 和 §4.2 之后修：用 pinned 内存在旁路流上搬运，或者让 id 留在设备上直到调度器真正需要它。

### 4.4 调度路径上的逐请求 Python

`sched + bld_meta + ci` 从 batch 1 到 1024 分别涨了 20 倍、9 倍、90 倍，合计 5.98 ms —— **占整步的
3.5 %**。今天还小，但它是除采样之外唯一随 batch 增长的成本，所以 §4.1 落地之后它就是下一个天花板。

## 5. 哪些**不是**瓶颈

* **LM head。** `logits_gpu` 在 batch 512 是 0.956 ms，对应 139 GFLOP 的矩阵乘 —— **146 TFLOP/s，
  达到显卡 BF16 峰值的 88 %**，是整个引擎里利用率最好的 kernel。
* **prefill 计算。** 8192 个 token 约 77 ms，即 **70 TFLOP/s（42 % MFU）**。健康；亏的是编排，不是
  算术。
* **调度策略和 KV cache。** 11 个 batch × 2 轮，零抢占、零 cache 耗尽、零重调度。
* **报出来的 TTFT。** 闭环产物 —— 所有请求在 t=0 全部入队，而同时只有 `batch` 个在跑。有意义的是
  `prefill` 字段（batch 1 时 23.4 ms，batch 1024 时 204.5 ms）。

## 6. 与 log914 相比变了什么

三件事同时变了，所以两轮 sweep **不能**直接对比：

| | log914 | log915 |
| --- | --- | --- |
| `pre_gather_cos_sin` | 声明为 false，但**被代码忽略** —— 实际走预取路径 | false 且**生效** —— 实际走逐层路径 |
| `use_d_first_schedule` | true | false |
| 主机 | 一台 vast.ai 实例 | 另一台 |
| tok/s @ 1024 | 5300 | 5095（−3.9 %） |
| `rope` @ 512 | 4.31 ms | 6.29 ms（+46 %） |
| decode 步 @ 512 | 92.35 ms | 100.17 ms（+8.5 %） |

* **`rope` 的退步是 flag，不是代码。** log914 的"baseline"在自己不知情的情况下一直开着预取。
  可与之对比的是 log915 开关矩阵里的 `pre_gather` 那一组，而不是这个 baseline。
* **调度开关不是混淆项。** batch 512 时两轮 sweep 都恰好产生 349 个 prefill 步和 965 个 decode 步
  —— 在所有请求预先入队的饱和闭环负载下，D-first 和交错调度收敛到相同的步结构。
* **主机是一个真实变量。** 这个引擎是 launch-bound 的，所以 host CPU 的速度对步时间的影响比迄今
  测过的任何开关都大。把 `torch.cuda.get_device_name()`、驱动版本、torch 版本和 CPU 型号记进 metrics
  头部，这些日志才能自描述；今天硬件身份只能靠正文交代。

## 7. 建议，按顺序

1. **把采样路径改成在候选集上工作**（§4.1）。唯一能把吞吐提升一个倍数的改动，而且通过 prefill 步
   再赚一次。batch 512 约 2 倍。
2. **给 decode 步做 CUDA graph**（§4.2）。唯一能改善延迟的改动，也是让所有 kernel 级优化的符号
   符合预期的前提。
3. **把 `pre_gather_cos_sin` 打开** —— 免费，本来就是 `config.py` 的默认值，值每步 1.6~10.9 %。
   开着它重跑这份 sweep；上面的数字低估了引擎这么多。
4. **解除 token 回读的阻塞**（§4.3），等步时间短到 5 ms 值得计较之后。
5. **把主机身份记进 metrics 头部**（§6），在租下一台实例之前。

## 8. 限定条件

* 两轮 sweep 在同一台实例上、40 分钟内跑完；**这个配置**没有跨机器复现。
* "采样占整轮"按设备侧窗口归属，窗口内的流空隙也被算了进去。batch ≥ 256 时 GPU 喂得饱，误差很小；
  batch 128 以下不是，所以这一列只从 128 往上读。
* 负载是合成的（随机 id、固定 512/128）。随机 id 会改变 penalty 掩码的密度（相对真实文本），
  这影响 §4.1 的内存流量，但不影响其渐进行为。
* MBU/MFU 按"decode 步完整读一遍 0.988 GB 权重"计算，这对模型主体是精确的，但忽略了 KV 流量
  （每 token 每步 12 KiB —— batch 512 时 6 MB，相对权重可忽略）。
