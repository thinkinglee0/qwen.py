# 性能分析 —— 恢复 fp32 后的采样器改动，两台宿主（log1013）

> 英文原版：[`performance_analysis_log1013.md`](./performance_analysis_log1013.md)

**这一轮测的是 [log1012](./performance_analysis_log1012.zh.md) 给出的建议**：保留 penalty 跳过与
稀疏 penalty 的改动，同时恢复 fp32 cast，并且只在 sampler 入口做一次。基线是 `main`，候选是
`perf/sampler-skip-and-sparse-penalty`。同一组 A/B 在同一天跑在两台实例上：

* **宿主 1**：一台慢、且 GPU 被限功耗的机器；
* **宿主 2**：项目迄今租到的最快宿主。

一句话版本：

* **两台宿主上的设备侧节省完全相同：batch 512 每步 6.6 ms。** 它能转化成多少吞吐，取决于宿主：
  * 宿主 1：batch 512 上 **+5.8 %**，因为它受主机侧限制；
  * 宿主 2：**+16.6 %**，因为它受 GPU 限制。
* **fp32 的代价比 log1012 说的大。** 恢复 fp32 在 batch 512 上每步多花 **5.1 ms** 设备时间，
  而不是 2.9 ms。在快宿主上，这大约是整步的四分之一。
* **计划里对 `smp_pick` 的两项预测偏高**（§3.4）。

**数据来源**（`log_vast/log1013/`）

| 内容 | 宿主 1 | 宿主 2 |
| --- | --- | --- |
| 并发 sweep，`main` / 候选 | `host1/benchmark_{baseline,sparse_pen}/` | `host2/benchmark_{baseline,sparse_pen}/` |
| 纯 decode profile，每臂 ×2 | `host1/profile_{baseline,baseline2,sparse_pen,sparse_pen2}/` | `host2/profile_…`（同名） |
| `main` 对候选的 step 指标对比 | `host1/baseline_against_sparse_pen/` | `host2/baseline_against_sparse_pen/` |
| run 间对比 | `host1/{baseline_against_baseline2,sparse_pen_against_sparse_pen2}/` | `host2/…`（同名） |
| 宿主清单 | `host1/{host_check.log,gpu.static.csv}` | `host2/{host_check.log,gpu.static.csv}` |

bf16 参照是 log1012 的 `smp_opt` 臂：`log_vast/log1012/{benchmark,profile}_smp_opt/`。

**被测代码**

| 臂 | ref | 差异 |
| --- | --- | --- |
| baseline | `main` @ `2c169ce` | — |
| sparse_pen | `perf/sampler-skip-and-sparse-penalty` @ `1bd9f72` = `main` + 一个提交 | `sampling.py`、`scheduler.py`、`model.py`、`tests/test_sampling.py` |

两台宿主的 run 之间，候选提交被 amend 过，从 `7b9b350` 变成 `1bd9f72`。只有
`tests/test_sampling.py` 改了，`src/` 逐字节相同，所以两台宿主跑的是同一份引擎代码。

与 log1012 的 `smp_opt` 臂相比，候选只有一处要紧的不同：`QwenForCausalLM.sampler()` 现在在入口调用
`logits.float()`。因此无论开关怎么设，penalty、温度、`topk`、softmax 和 `multinomial` 都在 fp32 上运行。

四次运行的配置完全相同，也与 log1012 一致：`temperature=0.7, top_k=20, top_p=0.8,
repetition_penalty=1.1, frequency_penalty=presence_penalty=0`、`compile_rope=false`、
`pre_gather_cos_sin=true`。**全部 44 个 sweep 点零抢占、零错误。**

## 摘要

1. **同一份代码在两台宿主上省下的设备时间相同，但吞吐收益相差约 3 倍：**

   | batch | 宿主 1 | 宿主 2 |
   | --- | --- | --- |
   | 256 | +1.1 % | **+16.0 %** |
   | 512 | +5.8 % | **+16.6 %** |
   | 1024 | +12.4 % | **+14.2 %** |

   batch ≤ 128 时两台宿主都在 ±1 % 以内。峰值吞吐：宿主 1 从 10 048 升到 10 630 tok/s，宿主 2 从
   11 137 升到 12 990。
2. **到目前测过的每台宿主上，设备工作量都相同。** batch 512 时，`main` 的 `smp_gpu` 在 log1012、
   宿主 1、宿主 2 上分别是 16.33 / 16.36 / 16.35 ms，候选在宿主 1、宿主 2 上是 9.771 / 9.772 ms。
   收益大小取决于主机侧能否跟上设备（§5）：
   * **宿主 2 的主机侧下限约 10–11 ms**，所以 batch 256–512 受 GPU 限制、空闲只有 3–7 %，6.6 ms 的
     节省全部体现在墙钟时间上（27.70 → 21.09 ms）。
   * **宿主 1 的主机侧下限约 25 ms**，所以 6.6 ms 里只拿回了 1.9 ms。
3. **penalty 的节省在 fp32 下依然成立。** 两台宿主上 batch 512 的 `smp_pen_gpu` 都从 **6.85 降到
   0.09 ms**。入口 cast（0.51 ms）现在落在这两个子区间之外。把它算进去，penalty 的净节省是
   **6.25 ms**。
4. **跑 fp32 而不是 bf16，在 batch 512 上每步多花 5.1 ms**（§4）。log1012 §6 只数了六个算子，估计
   约 2.9 ms，还说恢复 fp32 "墙钟时间 ≈ 0 ms"。**这两个说法都是错的。** 在受 GPU 限制的宿主 2 上，
   这 5.1 ms 大约是 decode 步的四分之一。这使得重写采样尾部（C2–C5）成为快宿主上的下一个抓手。
5. **在 fp32 下，`smp_pick_gpu` 只从 8.87 降到 8.52 ms（−0.34）**，全部来自 A3，即去掉 greedy
   `argmax`。计划把 A3 定价为 −0.76，因为它把一步里的两个 argmax 都算了进去，但其中一个在
   `multinomial` 内部。计划把 C1（原地温度缩放）定价为 −0.30，但 `div_` 搬运的字节和 `div` 一样，
   实测节省约为零（§3.4）。
6. **两台宿主有两处不同。**
   * **CPU。** 宿主 2 是 **Ryzen 9 7950X3D**（Zen 4），batch 1 的 `fwd` 是 8.35 ms，宿主 1 的
     EPYC 7K62 是 19.07 ms。batch 1 吞吐 99 对 44 tok/s。
   * **GPU 功耗上限。** 宿主 1 被限在 **260 W**，完整 8 k token 的 prefill 步因此要 69 ms，而宿主 2
     的 450 W 卡是 61 ms。decode 受带宽限制，不受影响。
7. **解释器循环跨 CPU 代际就不再能预测了。** 在三台 Zen 2 宿主上，`fwd`/循环 稳定在 0.068–0.072。
   在 Zen 4 X3D 上是 **0.055**：引擎比循环预测的快约 22 %（§6）。

## 1. 两台宿主

| | 宿主 1 | 宿主 2 | log1012（参照） |
| --- | --- | --- | --- |
| CPU | **AMD EPYC 7K62**，Zen 2 | **AMD Ryzen 9 7950X3D**，Zen 4，3D V-Cache | Ryzen 9 3900X，Zen 2 |
| 可见线程 / cgroup 配额 | 96 / **23.04** | 32 / 30.72 | 24 / 23.04 |
| 单核频率 | 3.25–3.27 GHz | **4.73–5.09 GHz** | 4.57 GHz |
| **解释器循环**（3 M 次迭代） | 271–289 ms | **148–155 ms** | 197–210 ms |
| 运行前被限流的周期 | 82 / 1 007 | 5 | 7 |
| GPU | RTX 4090，驱动 580.142 | RTX 4090，驱动 580.173.02 | RTX 4090，驱动 595.71.05 |
| **enforced 功耗上限** | **260 W** | 450 W | 450 W |
| PCIe | gen 4 × 16 | gen 4 × 16 | gen 4 × 16 |

**宿主 1 的 cgroup。** 23 核的配额摊在 96 个可见 CPU 上，所以全核测试里每个 CPU 只被调度了约 25 %
的时间。单核测试被调度 100 %，而引擎主循环是单线程的，所以主路径应该不受影响。

**宿主 2 运行前的负载。** 它的 `uptime` 显示负载均值 0.89 / 7.50 / 12.44，说明运行前不久有别的
租户在忙。到做宿主检查时机器已经安静：只有一个 CPU 1.5 % 忙。

**sweep 期间的 GPU**（利用率 ≥ 95 % 的样本）：

| | 宿主 1 基线 | 宿主 1 候选 | 宿主 2 基线 | 宿主 2 候选 |
| --- | --- | --- | --- | --- |
| SM 频率中位数 | 2 205 MHz | 2 085 MHz | 2 745 MHz | 2 745 MHz |
| 功耗中位数 | 259.5 W | 258.4 W | 389 W | 408 W |
| `sw_power_cap` 触发 | 96.6 % | 95.9 % | 9.7 % | 13.1 % |
| 最高温度 | 70 °C | 70 °C | 72 °C | 72 °C |

**260 W 上限改变了什么。** decode 的设备时间在每台宿主上都一样（§3.3），因为 decode 受带宽限制，
较低的 SM 频率拖不慢它。prefill 受计算限制，完整 8 k token 的 prefill 步就体现了这一点：

| | 宿主 1（260 W） | 宿主 2（450 W） | log1012（450 W） |
| --- | --- | --- | --- |
| 完整 prefill 的 `fwd_gpu`，`main`，batch 512 | 69.2 ms | 61.1 ms | 59.6 ms |

在宿主 1 上，候选的频率还比 `main` 低约 5 %，因为它在同样的 260 W 内每秒做了更多工作。如果说有偏差，
那也是让宿主 1 的对比略微不利于候选。

## 2. 方法与噪声

每台宿主上两臂都是背靠背跑的：

* **宿主 1**：候选 profile 01:39 和 01:45，然后 `main` profile 01:48 和 01:50，然后 `main` sweep
  01:53–02:08，然后候选 sweep 02:09–02:24；
* **宿主 2**：候选 profile 04:01 和 04:02，然后候选 sweep 04:05–04:13，然后 `main` profile 04:14
  和 04:16，然后 `main` sweep 04:18–04:27。

| | 宿主 1 基线 | 宿主 1 候选 | 宿主 2 基线 | 宿主 2 候选 |
| --- | --- | --- | --- | --- |
| 会话开头额外那次 batch 512 sweep | 1.4 % | 2.0 % | **0.9 %** | **1.2 %** |
| profile run 间，batch 1 `step_0` | +0.5 % | +1.3 % | −0.5 % | −0.2 % |
| profile run 间，batch 512 `step_0` | −0.1 % | −0.4 % | 0.0 % | +0.1 % |
| profile run 间，batch 512 `smp_gpu` | 0.0 % | 0.0 % | 0.0 % | 0.0 % |
| batch 512 异常步 | 1/20 | 1/20 | 0/20 | 0/20 |

宿主 2 是项目租到过的最安静的实例，吞吐噪声约 1 %；宿主 1 约 2 %。采样器的设备区间在两台宿主上
重复误差都在 0.03 % 以内。

batch 1 时，宿主 1 的 profile 对比显示候选慢 1.5 %。这几乎全部落在代码没改过的 `fwd` 和 `rope`
上，而宿主 1 的 sweep 显示的方向相反（+0.3 %），宿主 2 则是 −0.02 %。所以宿主 1 这 1.5 % 是 run 间
漂移，不是代码造成的变化。

和之前的报告一样，主机侧成为瓶颈时，`fwd_gpu`、`rope_gpu`、`logits_gpu` 这些 event 区间会被气泡撑大。
宿主 1 在 batch 512 上候选的 `fwd_gpu` 读出 +45 %。宿主 2 受 GPU 限制，`fwd_gpu` 不变
（10.36 对 10.33 ms）。应该信任的字段是 `gpu_busy_from_trace`。

两台宿主在每个设备区间上的差异都在 0.02 ms 以内。

* **cast 被计在哪里。** 在 `main` 上，fp32 提升发生在 `smp_pen` 内部，是
  `where(…, logits / rep, …)` 的副作用。候选里 cast 是显式的，位于 `smp_pen` 区间之前。所以
  `smp_pen` 看起来比 penalty 实际省下的多出 0.51 ms。
* **主机侧代价净为零。** `smp_prep` 多了一个恒定的 +0.05 到 +0.09 ms，来自主机侧三次
  `.any().item()` 开关读取和温度标志。`smp_run` 因为发射的算子更少，少了约 0.075 ms。两者都没有
  引入设备同步：`dth_wait` 没变。

### 3.4 算子（batch 512，宿主 1 的 profile；宿主 2 在 1 % 以内一致）

下表是 aten 总量除以 5 个 profile 步。这个 batch 上，表中每个算子都以采样器为主：

| 算子 | 基线 | 候选 | 变化原因 |
| --- | --- | --- | --- |
| `copy_` | 1.023 | 1.527 | **+0.50**：显式的 `logits.float()` |
| `where` | 1.532 | 0.030 | −1.50：稠密的 repetition `where` 没了（B3） |
| `mul` | 2.614 | 0.682 | −1.93：repetition 和 freq/pres 的乘法没了 |
| `sub` | 2.076 | 0.054 | −2.02：freq/pres 的减法被跳过（A2） |
| `bitwise_or`、`gt` | 0.541 | 0.005 | −0.54：`prompt_mask | output_mask`、`logits > 0` |
| `argmax` | 0.715（2 次调用） | 0.384（1 次调用） | **−0.33**：跳过 greedy argmax（A3） |
| `div` + `div_` | 2.504 | 1.664 | −0.84：稠密的 `logits / rep` 没了；温度除法不变 |
| `topk`、`_softmax`、`sum`、`masked_fill_`、`max`、`exponential_` | 5.109 | 5.116 | 不变：同样的 fp32 工作 |

**计划对 `smp_pick` 的两项预测偏高：**

* **A3，跳过 greedy argmax：预测 −0.76，实测 −0.33。** `main` 每步跑两次 `argmax`，但只有一次属于
  greedy 路径。另一次在 `torch.multinomial` 内部：采一个样本时它计算的是
  `argmax(probs / exponential_noise)`。这也解释了候选里还剩下的那一个 `exponential_`、一个 `div` 和
  一个 `argmax`。计划把两个 argmax 都算进去了。
* **C1，原地温度缩放：预测 −0.30，实测 ≈ 0。** 一次 fp32 `[512, 151 936]` 的除法，不管是不是原地，
  都要读 311 MB、写 311 MB。`div_` 省掉的是一次分配，不是内存流量。温度除法两种写法都是 0.66 ms。

## 4. fp32 相对 bf16 的代价

在这套设置下设备工作量可以跨宿主比较（§3.3），所以 log1012 的 bf16 `smp_opt` 臂可以直接和这次的
fp32 候选对比：

| batch 512，ms/步 | bf16（log1012 `smp_opt`） | fp32（log1013 候选） | fp32 代价 |
| --- | --- | --- | --- |
| `smp_run_gpu` | 4.033 | 9.127 / 9.129 | **+5.09** |
| `smp_pen_gpu` | 0.090 | 0.093 / 0.094 | — |
| `smp_pick_gpu` | 3.938 | 8.523 / 8.525 | +4.59 |
| 入口 cast（子区间之外） | 0.005 | 0.511 / 0.510 | +0.51 |
| `gpu_busy_from_trace` | 15 192 µs | 20 307 / 20 385 µs | +5.1 到 +5.2 |

按算子拆开 fp32 的代价（宿主 1，每步）：

| 算子 | bf16 | fp32 | Δ |
| --- | --- | --- | --- |
| `topk` | 0.719 | 1.859 | +1.14 |
| `copy_`（入口 cast，及其他拷贝） | 0.686 | 1.527 | +0.84 |
| `_softmax` | 0.429 | 1.256 | +0.83 |
| `div`（`multinomial` 内部） | 0.497 | 1.001 | +0.50 |
| `sum` | 0.352 | 0.694 | +0.34 |
| `masked_fill_` | 0.380 | 0.675 | +0.30 |
| `div_`（温度） | 0.379 | 0.663 | +0.28 |
| `fill_`（`full_like(-inf)`） | 0.571 | 0.735 | +0.16 |
| `argmax`（`multinomial` 内部） | 0.222 | 0.384 | +0.16 |
| `max`、`exponential_` | 0.325 | 0.632 | +0.31 |
| **合计** | | | **+4.86** |

**对 log1012 §6 的更正。** 那一节列了六个算子，估计约 2.9 ms。它漏掉了：

* cast 本身；
* `multinomial` 内部的 `div` 和 `argmax`；
* 温度的 `div_`；
* `full_like` 填充。

它接着得出结论：因为 3900X 在 batch 512 上有 4.8 ms 的设备空闲，恢复 fp32 "墙钟时间 ≈ 0 ms"。
实测代价是 5.1 ms，所以那台宿主上的 fp32 步本会勉强变成受 GPU 限制。

**在宿主 2 上，这个代价完全显现。** 宿主 2 在 batch 512 上受 GPU 限制，空闲 3.4 %，主机侧下限远低于
15 ms。如果用 bf16，它的步长大约是 15.2 ms 设备时间加一点残余，约 15.9 ms 墙钟时间，而 fp32 实测是
21.09 ms。所以在这台宿主上，fp32 大约占 **batch 512 decode 步的四分之一**。这是根据可跨宿主比较的
设备时间做的推算，宿主 2 上没有跑过 bf16。

这些都不是回到 bf16 的理由，计划里的数值精度论证依然成立。fp32 的代价大部分在 `[B, V]` 的采样尾部：
`topk`、softmax、`multinomial`、温度除法和 `-inf` 填充。这正是 C2–C5 把计算挪进 `[B, max_k]` 窗口后
会去掉的工作：保留 fp32，同时去掉它的大部分代价。

## 5. 为什么同样的节省收益差这么多

一个 decode 步的墙钟时间大致是 `max(主机侧时间, 设备时间)`：

| batch 512 | 宿主 1 | 宿主 2 |
| --- | --- | --- |
| 主机侧下限（batch 128–256 仍受主机侧限制时的墙钟时间） | **约 25–26 ms** | **约 10–11 ms** |
| 设备步长，`main` → 候选 | 26.9 → 20.3 ms | 27.0 → 20.4 ms |
| 瓶颈，`main` → 候选 | 设备 → **主机** | 设备 → 设备 |
| 省下的墙钟 / 省下的设备时间 | 1.9 / 6.6 ms | **6.6 / 6.6 ms** |

* **宿主 1 在节省的中途从受设备限制翻转为受主机限制**，所以大部分节省变成了空闲（23.9 %）。
* **宿主 2 始终受设备限制**，所以全部节省都到达了墙钟时间，batch 256 也一起受益。宿主 2 上
  `main` 在 batch 256 就已经受 GPU 限制（空闲 5.5 %），候选把这一步从 15.79 ms 降到 12.45 ms。

**batch 1024 的 decode 在两台宿主上完全一样。** 候选的 sweep decode 步长在两边都是 37.67 ms。这个
batch 上两台宿主之间 1 121 tok/s 的差距全部来自 prefill：104.2 s 对 93.4 s，也就是 260 W 上限。

这对优先级意味着：

* **快宿主（宿主 2 这一类）：** 从 batch 256 起 GPU 就是瓶颈。剩下的采样器工作能全额兑现：C2–C5
  对应 8.5 ms 的 fp32 尾部，D1/D2 对应 `smp_prep_gpu` 里的 0.6 ms。
* **慢宿主（宿主 1 这一类）：** 主机侧下限卡住了所有 batch ≤ 512 的情况。那里的抓手是每步的主机侧
  时间，首先是给 `fwd` 上 decode CUDA graph。

## 6. 跨宿主对比，以及解释器循环

| 宿主 | 架构 | 循环（ms） | batch 1 `fwd`（ms，`main`） | `fwd` / 循环 | batch 1 tok/s |
| --- | --- | --- | --- | --- | --- |
| log1011 EPYC 7452 | Zen 2 | 263–271 | 19.15 | 0.072 | 44 |
| log1013 宿主 1，EPYC 7K62 | Zen 2 | 271–289 | 19.07 | 0.068 | 44 |
| log1012 Ryzen 3900X | Zen 2 | 197–210 | 14.31 | 0.070 | 58 |
| **log1013 宿主 2，Ryzen 7950X3D** | **Zen 4** | **148–155** | **8.35** | **0.055** | **99** |

在 Zen 2 内部，3 M 次迭代的循环能很好地预测这个引擎的主机侧开销：在 1.4 倍的速度范围里，
`fwd`/循环 稳定在 0.068–0.072。**它推广不到 Zen 4。** 循环说 7950X3D 比 3900X 快 1.35 倍，
但 `fwd` 快了 1.71 倍。

batch 1 的 `fwd` 主要花在 PyTorch 的 dispatcher 和 kernel 发射路径上，它的工作集比一个紧凑的字节码
循环大。Zen 4 更高的 IPC 和 X3D 的 128 MB L3，对前者的帮助很可能大于对后者的帮助。本报告无法把
这两个因素分开。

这个循环仍然适合用来排除慢宿主，但它不能替代直接测 `fwd`。最快的替代指标是单个 sweep 点的
batch 1 TPOT：宿主 2 是 10.1 ms，宿主 1 是 22.8 ms。

## 7. 注意事项

1. **每台宿主每臂只有一次 sweep。** 每个 pytest 会话开头额外那次 batch 512 运行只重复了这一个点：
   0.9–2.0 %。
2. **两臂没有交错运行。**
   * 宿主 1 上，候选先跑 profile，但 `main` 先跑 sweep。
   * 宿主 2 上，候选全程先跑。

   run 间漂移在宿主 1 上约 1 %，在宿主 2 上低于 0.5 %。
3. **宿主 1 上两臂都跑在 260 W 上限，候选的 SM 频率还低约 5 %。** decode 设备时间不受影响，但
   宿主 1 sweep 里 prefill 的那部分略微不利于候选。
4. **宿主 1 的 cgroup 配额（96 个里 23 个）以及一个 CPU 上 99.5 % 忙的邻居**，在运行期间都没有测量。
   宿主 2 运行前不久有租户负载（15 分钟负载均值 12.4），但在宿主检查时是安静的。
5. **§4 的 bf16 对比和宿主 2 的推算是跨宿主的。** 它们依赖设备时间可以跨宿主比较，三台宿主目前在
   0.1 % 以内支持这一点。bf16 本身从没在宿主 1 或宿主 2 上跑过。
6. **§3.4 和 §4 的算子归因用的是整步的 aten 总量。** batch 512 上列出的算子以采样器的 `[B, V]` 调用
   为主，但也包含了模型侧的小调用。

## 8. 接下来

1. **合并候选分支。**
   * fp32 cast 是显式的，不依赖哪些 penalty 打开，这正是计划要求的性质。
   * 两台宿主上 batch ≤ 128 不变，batch ≥ 256 都更快。
   * 合并前，按计划跑一次固定种子的逐 token 对比，对照 `main`。两臂都在 fp32 上计算，并以相同顺序
     消耗 RNG，所以应该一致。
2. **接下来做 C2–C5。** 在宿主 2 这类机器上，它们现在承载着最大的采样器收益：batch 512 上 8.5 ms 的
   fp32 尾部，而这一步受 GPU 限制。用本报告的更正更新计划：
   * A3 值 −0.33，而不是 −0.76；
   * C1 约等于 0；
   * `multinomial` 内部的 `div`/`argmax`/`exponential_`（fp32 下约 1.7 ms）就是 C5 的 Gumbel-max
     要替换的部分。
3. **落地 D1/D2。** 两台宿主上 batch 512 的 `smp_prep_gpu` 仍是 0.60 ms。在宿主 2 上，这就是墙钟时间。
4. **给 `fwd` 上 decode CUDA graph**，这仍是宿主 1 这类机器、以及所有宿主上 batch ≤ 128 的抓手。
5. **更正 log1012 §6。** fp32 的代价是 5.1 ms 而不是 2.9 ms，也塞不进 3900X 的空闲时间。指向本报告 §4。
6. **租机门槛。**
   * 检查 `enforced.power.limit`：260 W 相对 450 W，prefill 大约慢 13 %。
   * 跨 CPU 代际时，把解释器循环当作下限检查，而不是预测器（§6）。
   * 采样器和模型相关的工作优先用宿主 2 这一类机器。只有在这类机器上，设备侧的改动才会完整体现在
     吞吐上。
